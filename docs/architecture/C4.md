# Journey — Architecture (C4 model)

Status: **Living**
Last updated: 2026-07-30

> [C4](https://c4model.com) describes software at four zoom levels: **Context →
> Container → Component → Code**. We maintain the top three as Mermaid (the Code level is
> the source itself), plus a Deployment view. See `docs/ARCHITECTURE.md` for the
> rationale, ADR-0001/0002 for the app decisions, ADR-0005 for the data-layer seams,
> and `docs/DEPLOY.md` for the deployment runbook.

---

## Level 3 — Components

### Frontend (SPA) — maps to `src/`

```mermaid
flowchart TB
    subgraph features[features/ · React UI slices]
        canvas[canvas]
        panel[panel]
        traits[traits]
        auth[auth]
        app[app shell]
    end
    state[state/ · Zustand stores<br/>graph, camera, selection, drag, choose, auth, journeys]
    domain[domain/ · pure TS<br/>graph/DAG, geometry/LOD, status, color, types]
    render[render/ · PixiJS adapter<br/>CanvasRenderer + canvasBridge]
    apiclient[api/ · HTTP client]

    features -->|read + dispatch| state
    state -->|pure logic| domain
    render -->|subscribes to| state
    render -->|hit-test / create goal| domain
    canvas -->|mounts| render
    features -->|calls| apiclient
    apiclient -->|HTTP| server[(API)]
```

**Key seam:** the `render` layer never owns state — it subscribes to `state` and uses
`domain` for pure math. React never re-renders the WebGL scene (ADR-0002).

### Backend (API) — maps to `server/`

Data access and file storage sit behind seams (ADR-0005) so the DB and file
backends can be swapped without touching the routes.

```mermaid
flowchart TB
    routes[index.mjs · Express routes + helpers<br/>auth · journeys · attachments · telegram · instagram · /health]
    config[config.mjs · env / config 12-factor]
    dbmod[db.mjs · openDatabase<br/>schema + migrations]
    storage[storage.mjs · file-storage interface]
    telegram[telegram.mjs · ingestion worker]
    ai[ai.mjs · transcribe + structure]
    db[(SQLite · node:sqlite)]
    files[(attachments · local FS)]
    openai[OpenAI]
    spa[[built SPA · dist/]]

    routes -->|reads| config
    routes -->|SQL via| dbmod
    dbmod --> db
    routes -->|files via| storage
    storage --> files
    routes -->|serves in prod| spa
    routes --> telegram
    routes --> ai
    ai --> openai
    telegram -->|db + files today| db
    telegram --> files
```

**Swap seams (ADR-0005):** `db.mjs` is the point to move to Turso/libSQL or
Postgres; `storage.mjs` is the point to move to S3/R2. Routes stay unchanged.
The Telegram worker still touches `db` + files directly (a documented follow-up).

## Deployment — home + Tailscale (personal)

One always-on instance on a machine you own, reached privately over Tailscale
(`tailscale serve` gives it HTTPS so the session cookie works). See `docs/DEPLOY.md`.

```mermaid
flowchart LR
    subgraph devices[Your devices]
        laptop([Laptop])
        phone([Phone])
    end
    subgraph tailnet[Tailscale tailnet · private mesh]
        subgraph box[Home machine]
            serve[tailscale serve<br/>HTTPS endpoint]
            node[node server/index.mjs<br/>API + SPA · :8787]
            data[(~/.journey<br/>journey.db + attachments)]
            serve --> node
            node --- data
        end
    end
    backup[[Backup · cron / Litestream]]

    laptop -->|HTTPS| serve
    phone -->|HTTPS| serve
    data -.-> backup
```

**Going public later:** swap `db.mjs` → Turso/Postgres and `storage.mjs` → S3/R2,
host on Fly.io/Render (persistent volume), add a PWA for mobile. The SPA, domain,
API, and tests are backend-agnostic, so it's a contained migration.
